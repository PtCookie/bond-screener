# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

An Astro-based web application that queries the two Financial Services Commission bond open APIs (basic info, price info) published on the Korean public data portal (data.go.kr). The interactive UI is built with the React Islands pattern, and the app is deployed to Cloudflare Workers.

## Commands

```bash
pnpm run dev              # Start the dev server (localhost:4321)
pnpm run build            # Production build (./dist/)
pnpm run preview          # Preview the build output locally
pnpm run lint             # Run ESLint
pnpm run format           # Run Prettier formatting
pnpm run test             # Run Vitest in watch mode (three projects: node/browser/workers)
pnpm run test --run       # Run Vitest once (same as CI/hooks)
pnpm run test <file>      # Run tests for a specific file
pnpm run test --project=browser --run   # Run only Browser Mode (React components/hooks)
pnpm run test:e2e         # Run Playwright E2E (seeds the E2E-only D1 → webServer starts pnpm dev automatically)
node scripts/seed-e2e.mjs  # Rebuild only the E2E-only local D1 (.wrangler/e2e-state)
pnpm generate-types   # Generate Cloudflare binding types from wrangler.jsonc (worker-configuration.d.ts)
pnpm deploy           # Build and deploy to Cloudflare Workers (astro build && wrangler deploy)
pnpm prepare          # Install lefthook (runs automatically on first setup)

# Check remote deployment state (code cannot tell you whether a secret/migration/backfill actually landed):
wrangler secret list --config ./wrangler.jsonc
wrangler d1 migrations list bond-screener --remote --config ./wrangler.jsonc
wrangler d1 execute bond-screener --remote --config ./wrangler.jsonc --command "SELECT COUNT(*) FROM bond"
```

## Known Issues

- **Do not remove the `isVitest` branch in `astro.config.mjs` (which disables `adapter` under vitest).** The root cause has been established empirically: `@astrojs/cloudflare@14.1.3` registers its Worker environment as `viteEnvironment: { name: "ssr" }`, but Vitest 4.1.10 unconditionally overwrites `resolve.external` for **every** environment in its `configEnvironment` hook with `[...builtinModules, ...builtinModules.map(m => "node:"+m)]`. `validateWorkerEnvironmentOptions` in `@cloudflare/vite-plugin@1.45.1` accepts that value as long as it contains "node builtins only", but Node 24's `builtinModules` already includes four entries carrying the `node:` prefix (`node:sea`/`node:sqlite`/`node:test`/`node:test/reporters`), and Vitest does not filter them out — it prefixes them a second time, producing four double-prefixed values like `node:node:sqlite`. Those are not in the plugin's allowed set, so validation fails and `pnpm run test` cannot even start. In other words, the cause is **a one-line difference in how the two libraries handle the node builtin prefix**, and until one side fixes it this workaround is the only solution.
- In Claude Code sessions, tests must be invoked **in the `pnpm run test ...` form** — it has to match `sandbox.excludedCommands` (`pnpm run test*`) in `.claude/settings.json` in order to run outside the sandbox with full host privileges (`pnpm exec vitest` does not match, and Chromium dies inside the sandbox). Also, inserting `--` as in `pnpm run test -- --project=browser` breaks vitest's option parsing — write it attached, as in `pnpm run test --project=browser --run`.
- D1 local mode (`wrangler d1 execute --local`) requires `sandbox.network.allowLocalBinding: true` (same settings file) to work. It is already enabled — do not remove it.
- The `meta` of local (Miniflare) `wrangler d1 execute --local --json` has no `rows_written` (only `duration`) — that is a remote-only field. When adding logic that depends on local write counts, include a `null`-tolerant fallback (see `executeSqlFile` in `scripts/backfill.mjs`).
- The `wrangler` subprocesses that `scripts/backfill.mjs`/`scripts/build-snapshot.mjs` spawn via `execFileSync` run *inside* the sandbox unless the top-level Bash command is itself `pnpm exec wrangler ...` (e.g. `pnpm backfill apply ...` does not match `sandbox.excludedCommands`). The telemetry call wrangler sends by default (`sparrow.cloudflare.com`) is blocked by the sandbox network policy, which makes the whole command fail silently — so both scripts pass `WRANGLER_ENV` (`WRANGLER_SEND_METRICS=false`) from `scripts/lib/wrangler-config.mjs` as the `env` of those `execFileSync` calls, turning telemetry off entirely. Pass this `env` whenever you add a new `execFileSync(..., "wrangler", ...)` call as well.
- wrangler's OAuth login token tries to refresh itself when it expires, but in a non-interactive environment (scheduled jobs/script runs) it cannot re-authenticate through a browser, so `wrangler whoami`/`d1 execute` and friends fail with "Not logged in. Your auth token has expired...". In that case the user has to run `wrangler login` again from an interactive terminal; to fully automate this as a scheduled job, consider registering a `CLOUDFLARE_API_TOKEN` environment variable (API-token auth instead of OAuth).
- `pnpm add`/`pnpm install` may fail in the sandbox with `[ERR_PNPM_UNEXPECTED_STORE]` (the store `node_modules` is linked to differs from the store path pnpm wants to write to) — run it with `--store-dir /Users/cookie/Library/pnpm/store/v11`.
- **Do not use `client:load` for an island that downloads no data from the server and relies purely on client-side fetching** — `BondScreener` in `index.astro` (`useScreenerData` fetches `/api/snapshot/*` on the client, so SSR always renders nothing but the loading skeleton) actually hit this bug. `dist/client.js` of `@astrojs/react@6.0.1` deletes the `__reactContainer` key and calls `hydrateRoot` again even when the island is already hydrated (detected via `isAlreadyHydrated`) — so when the browser restores, via back/forward, a DOM that was already active with data loaded from the previous visit, and this re-hydration then runs, the client's first render (filters and data both at their initial values → buttons `disabled`) disagrees with the restored DOM (load complete → not `disabled`), producing a React hydration mismatch console warning (it appears as `disabled={true}` vs `disabled={null}`; empirically confirmed: cold SSR HTML always already carries `disabled`, so it does not reproduce on first load, only on back-navigation restore). Switching to `client:only="react"` removes the server-HTML comparison step altogether, so the problem disappears structurally — an island whose data the server actually passes down as props (`BondDetail` in `bond/[id].astro`) is unaffected, so keep `client:load` there.
- `pnpm add`/`pnpm install` fails with `[ERR_PNPM_EPERM] ... copyfile ... .vscode/settings.json` when the dependency tree contains a package that ships a `.vscode/settings.json` (e.g. `stream-replace-string`, pulled in by `@astrojs/sitemap`) — the sandbox blocks, by policy, any write whose path contains `.vscode/` (protection against supply-chain attacks that target editor auto-run settings). pnpm options such as `--package-import-method=copy` do not work around it — ask the user to run `pnpm add` (including the `--store-dir` above) directly in their terminal.
- A Custom Domain can be attached from `wrangler.jsonc` alone, with no dashboard interaction: `"workers_dev": false` + `"routes": [{ "pattern": "<domain>", "custom_domain": true }]`, then `wrangler deploy` — Cloudflare handles DNS records and certificate issuance automatically.
- Since `@astrojs/cloudflare` 14.2.x, the build-time default for `imageService` changed to `cloudflare-binding`, which auto-enables the `IMAGES`/`SESSION` bindings and emits a warning — if you use neither `<Image>` from `astro:assets` nor Astro Sessions (this project uses neither), it is a harmless warning, so do not force those bindings into `wrangler.jsonc`.
- The Workers Rate Limiting binding (`ratelimits`, `env.<NAME>.limit({key})`) does not rate limit at all under local `astro dev`/Miniflare (measured: 40 consecutive requests all returned 200) — wrangler's binding support table lists `ratelimit: "local-only"`, but there is no actual local simulator. Always verify in production after deploying. The counter is also **per Cloudflare location (colo)** rather than global, so the same client may hit a different counter on each request (an approximation by design, as stated in the official docs) — use it only as an abuse-prevention approximation, not as an exact global limit.
- **Do not remove the settings that exclude `.claude/worktrees/<name>/` (git worktrees created inside the repo root) from Vite/Vitest watching and collection.** That directory, created by other Claude Code sessions, is a full copy of the repository (including its own `tsconfig.json`, `tests/`, and `node_modules`) and is git-ignored via `.git/info/exclude`, but neither Vite nor Vitest reads that file, which causes two problems. ① The default include of `vitest.node.config.ts` (`**/*.{test,spec}.*`) collects the worktree copy's `tests/**` wholesale, dragging browser-only tests into the forks pool and failing them en masse with `vitest/browser can be imported only inside the Browser Mode` (measured: the node project collected 92 files instead of 29, with 34 failures) — blocked by adding `.claude/**` to `exclude`. ② When Vite's watcher picks up an add/change event for the worktree's `tsconfig.json`, `reloadOnTsconfigChange()` fires `moduleGraph.invalidateAll()` + `full-reload` for **every** environment (empirically confirmed in vite 8.2.2, `dist/node/chunks/node.js:3546`). If another session creates or deletes a worktree while `pnpm dev` is running, you get unexplained full reloads — blocked by `vite.server.watch.ignored` in `astro.config.mjs` (shared by the node and browser projects and by `pnpm dev`) plus the same setting in `vitest.workers.config.ts` (needed separately because it does not go through `getViteConfig()`). Vite **appends** this value to its own default list, so there is no risk of overwriting. **Note that ② cannot be the cause of a `pnpm run test --run` (pre-push) failure** — in run mode Vitest sets `viteConfig.server.watch = null` and does `await server.watcher.close()` (`configResolved`/`configureServer` in `vitest@4.1.11`'s `dist/chunks/cli-api.*.js`), and `@vitest/browser` starts its own Vite server with `server: { hmr: false, watch: null }` outright (`createBrowserServer` in `dist/index.js`). That is, there is no watcher at all while tests run. The real cause of the phantom `Failed to import test file ... SyntaxError` failures this entry used to explain is the separate item below (dependency pre-bundle regeneration).
- **When several files in the browser project die at once with `Failed to import test file ... SyntaxError`, it collided with a dependency pre-bundle regeneration — it is not a source-code problem.** Measured case: in `git push`'s pre-push (`pnpm run test --run`), all 5 chromium files failed with `SyntaxError: Unexpected token '}'`, while the very top of that run's log showed `[vite] (client) Re-optimizing dependencies because vite config has changed` → `[optimizer] bundling dependencies...`, and the failing files were the ones that came up right as the browser stage started. Vite deletes and re-bundles the whole `deps` directory whenever `lockfileHash`/`configHash` in `node_modules/.vite/vitest/<sha1(project name)>/deps/_metadata.json` differ from the current values (`loadCachedDepOptimizationMetadata`, vite 8.2.2 `dist/node/chunks/node.js:32147`), while Vitest browser mode spins up all three browser pools with `Promise.all` as soon as the Vite server is listening and pulls test files in via native `import()`. So when the re-bundle and the imports overlap, only the files in flight at that moment break, and since the `SyntaxError` comes from an optimized chunk the test file pulled in rather than from the test file itself, multiple files show the **identical** message. Browser mode starts its Vite server with `hmr: false`, so Vite's usual recovery mechanism for this situation (full-reload) does not work either. `configHash` is computed from `resolve`, the plugin name list, and `optimizeDeps.include/exclude`, and `lockfileHash` from the contents of `pnpm-lock.yaml`, so it only blows up on **the first test run after changing config or dependencies** (= `git push` right after a commit) and passes on an immediate retry once the cache has been refreshed — lefthook is not the cause. **`optimizeDeps.noDiscovery`/`include` in `vitest.browser.config.ts` prevents this, so do not remove them** — with `noDiscovery: true` plus a non-empty `include`, Vite uses `createExplicitDepsOptimizer` instead of the default `createDepsOptimizer` (same file, 35505 and 34701), and its `init()` **awaits** the bundling and `commit()` of `optimizeExplicitEnvironmentDeps` (32115). That `init()` is awaited by `EnvironmentInstance.listen()` (35537), and `@vitest/browser`'s `createBrowserServer` starts the browsers only after `await vite.listen()` returns — i.e. the race window disappears entirely. The default optimizer's `init()` merely registers the scan promise and returns immediately (34451), which is why bundling keeps running past listen; that is the core of this bug. The trade-off is that dependencies not listed in `include` are loaded from source without pre-bundling (slower, but not a failure), so add any new runtime dependency used by a test to that list. To force a repro, change `configHash` in the browser cache's `_metadata.json` (`sha1("browser")` = `ef98362b…`) to an arbitrary value and run `pnpm run test --run` — but **it is timing-dependent and does not reproduce every time** (0 out of 8 runs before the fix; 1 out of 3 under conditions where re-optimization had become unstable). When it does reproduce, webkit reports `SyntaxError: Unexpected identifier 'path'. Expected '}' to end an object literal.` and chromium reports `SyntaxError: Unexpected token '}'` — **different messages per engine**. Both are the same symptom, so do not conclude from the wording that it is a different problem.

## Architecture

### Astro + React Islands

`.astro` files are rendered on the server, and React is used via `client:*` directives only for components that need interactivity (e.g. `<BondTable client:load />`).

### Data-fetching pattern

Open API calls are isolated in `src/lib/` or `src/api/`. The default pattern is to fetch initial data server-side in an Astro page and pass it to the React island as props.

### Cloudflare deployment

Uses the `@astrojs/cloudflare` adapter, with `output: "server"` already set in `astro.config.mjs`. `main` in `wrangler.jsonc` points at the custom entrypoint `src/worker.ts` rather than the adapter entrypoint — this is to add the cron `scheduled` handler (see the "Data layer" section below). `src/worker.ts` delegates `fetch` straight to `handle` from `@astrojs/cloudflare/handler`, so Astro routing behaves exactly as before. Secrets (`serviceKey` etc.) and bindings are accessed via `import { env } from "cloudflare:workers"` — the installed `@astrojs/cloudflare` (Astro v6+ compatible, v14.1.3) removed `Astro.locals.runtime.env` and throws immediately on access (empirically confirmed in `createLocals` in `node_modules/@astrojs/cloudflare/dist/utils/cf-helpers.js`). Do not follow the `Astro.locals.runtime.env` pattern from older adapter docs and examples.
- **Local development** (`pnpm dev`/`wrangler dev`): put values in a `.dev.vars` or `.env` file at the project root in `KEY="VALUE"` form. **Use only one of the two** — if `.dev.vars` exists, values in `.env` are ignored. The open API auth key goes in under the name `BOND_API_SERVICE_KEY` (`.claude/skills/probe-bond-api` looks for that name).
- **Deployment** (`wrangler deploy`): `.dev.vars`/`.env` are local-only and are not passed to the deployed Worker. You must register the secret with the Cloudflare platform via `wrangler secret put <NAME>`; `wrangler deploy` then binds the registered value as-is.
- Never commit `.dev.vars` or `.env` (they are registered in `.gitignore` as the `.dev.vars*` and `.env*` patterns).
- After changing binding types, refresh `worker-configuration.d.ts` with `pnpm generate-types`.
- Always pass `--config ./wrangler.jsonc` explicitly to D1/R2 CLI commands (`wrangler d1 execute`, `wrangler r2 object put`, etc.) — to avoid confusion with the deploy redirect to the build output (`dist/server/wrangler.json`).

### Data layer (D1 + R2 + cron)

Because of the daily call quota (10,000 calls on a development account) and the secret-exposure problem, clients do not call the open API directly. The structure is `Client → Workers(cron) → data.go.kr`: the Workers scrape the data ahead of time each day, store it in D1, and upload static snapshots to R2, so clients only receive the R2 snapshots (cutting D1 read costs — the list-query path never touches D1 at all).

**We have been on the Workers Paid plan since 2026-09-01.** The "free tier CPU 10ms/invocation" constraint referenced throughout this section no longer applies (the Paid cron CPU limit is 30 seconds for intervals under an hour). Two designs that had been split apart because of that constraint have now been merged: ① the screener list snapshot build now runs automatically inside cron (`src/lib/snapshot/build.ts`, see the "Weekly snapshot" section below), and ② a cron tick processes multiple pages per invocation (see the "cron pipeline" section below). **However, isolate memory (128MB) is a constraint common to Free and Paid, so it remains** — when adding code that reads an entire D1 table, as the snapshot does, do not reach for a full `all()` just because the CPU budget got roomier; always stream chunks in with keyset pagination (see `src/lib/d1/snapshot-repo.ts`/`src/lib/snapshot/build.ts` — local measurement showed peak heap of ~85MB when holding the entire `bond` table (29,079 rows) as an array of objects).

**If you modified `src/lib/sync/`, `src/lib/snapshot/`, or `src/lib/d1/`, review it with the `snapshot-sync-reviewer` subagent.** The full checklist of this layer's invariants, along with the symptoms that actually occurred and the measurements behind each item when they were violated, is collected in `.claude/agents/snapshot-sync-reviewer.md` — the items below keep only the summary (design and rules) and leave the detailed background there.

- **Schema**: `migrations/0001_init.sql` (`bond`/`bond_state`/`bond_price`/`code_label`/`sync_run`/`app_meta`), `migrations/0002_indexes.sql` (`idx_bond_expr_dt`/`idx_bond_srtn_cd`, applied on 2026-08-28 after the backfill completed). During the backfill, having indexes doubled the counted D1 writes, which is why they were parked in `migrations/pending/` — when adding a new index on a table involved in a bulk backfill, consider the same pattern (keep it in pending, move it once the backfill is done).
- **fetch/normalization**: `src/lib/openapi/` (shared client, error classification, normalization of `""`/`" "`/`"NULL"`), `src/lib/bond/` (`columns.ts` as the source of truth for column order, `mappers.ts` for mapping, `fingerprint.ts` for change-detection fingerprints).
- **D1 access**: `src/lib/d1/sql.ts` generates SQL that bulk-upserts in a single query by carrying an array in one parameter via `json_each(?1)` (working around the 100-bound-parameter-per-query limit — that limit is unchanged regardless of plan, so the technique is still needed). Always run new upsert SQL through the `buildInsertSelect` helper — it defends against SQLite syntax traps like the `WHERE true` dummy clause in exactly one place.
- **cron pipeline**: `scheduled` in `src/worker.ts` → `src/lib/sync/tick.ts` (`runSyncTick`). Within one tick (1-minute interval) it keeps processing pages until it reaches whichever budget comes first, `TICK_WALL_BUDGET_MS` (20 seconds) or `MAX_PAGES_PER_TICK` (40) (`src/lib/sync/config.ts`) — the practical ceiling is not CPU but open API response latency (wall clock). `runPagesUntilBudget` re-reads the cursor from D1 after processing each page to decide whether progress was made (so it does not pointlessly retry a page that backoff prevented it from advancing past). **Since 2026-09, basic info (`issu`) is collected every business day, just like prices** (it used to be once a week on a designated weekday). Once `issu` reaches `done` for today's target basDt, the screener snapshot pipeline automatically follows on **the next tick** (see the "Screener snapshot" section below) — on the full base rebuild weekday (`SNAPSHOT_REBUILD_WEEKDAY_KST`, Wednesday by default) it is the `snapshot` action, and on other weekdays the `bondDelta` action, which carries only that day's changes. `planTick` decides by comparing `snapshot_bas_dt`/`bond_delta_bas_dt` in `app_meta` against that basDt; unlike the `sync_run` used for basic info, these two do not create dedicated `sync_run` rows (a deliberate design choice to avoid a zombie run blocking the whole pipeline).
- **`sync_run.status` distinguishes `done` from `empty`.** Because the open API refreshes only after 1 p.m. on business day + 1, a cron query that runs earlier gets 0 rows — `finishSyncRun` closes the run as `empty` when `totalCount===0`, and `planTick` treats `empty` as a retry candidate identical to not-started (`null`), except that it must wait out `EMPTY_RETRY_BACKOFF_MS` (15 minutes, `src/lib/sync/config.ts`) before restarting (elapsed time is judged solely from the existing `finished_at`/`updated_at` — no new column). **When restarting from `empty`/`failed`, `startSyncRun` resets the cursor, the running totals, and the error (`next_page`/`total_count`/`rows_seen`/`rows_written`/`finished_at`/`error`) completely** — `tests/workers/sync-run-repo.test.ts`/`tick.test.ts` guard against regressions.
- **D1 counts writes twice on a TEXT PRIMARY KEY table that lacks `WITHOUT ROWID`** (SQLite's implicit PK index — inserting 29,079 `bond` rows measured as 58,158 writes). If a new table's PK is TEXT, always evaluate whether it should be `WITHOUT ROWID`.
- **`wrangler d1 execute --file` fails with `SQLITE_TOOBIG` when a single SQL statement exceeds 100,000 bytes.** Bulk INSERTs must be chunked by byte budget, not by row count — `buildMultiValuesInsert` in `scripts/lib/sql-gen.mjs` already does this (it also tracks each table's actual write multiplier via `writeMultiplier` to manage the daily write budget), so run new backfill SQL through that helper too.
- **Tests**: vitest runs **three projects** via `test.projects` (`vitest.config.ts` is the orchestrator). Pure logic that needs no bindings goes in **node** (`tests/*.test.ts`, `tests/scripts/**`), React components and hooks that need a DOM go in **browser** (`tests/components/**`/`tests/hooks/**`, Vitest Browser Mode — not jsdom), and anything requiring D1/R2 bindings goes in **workers** (`tests/workers/**`, real workerd). User flows are Playwright E2E (`e2e/**`) — **always run them with `pnpm run test:e2e`** (that script first runs `scripts/seed-e2e.mjs` to plant the migrations and the detail-page fixture (`e2e/fixtures/detail.sql`) into the E2E-only local D1 (`.wrangler/e2e-state`, separate from the real development data in `.wrangler/state`). Calling `pnpm exec playwright test` directly skips that seed, breaking the `/bond/[id]` tests with a 500). **When writing or modifying tests, or when a failure's cause is unclear, consult the `test-suite` skill** — it collects the per-project traps (Browser Mode's async `render`, Portal scoping, `autoResetPageIndex`; workers' per-file storage isolation and spy ordering; E2E selector collisions, retry timeouts, `astro dev` daemon issues, port 4321 being taken) and the settings that must not be deleted.
- **Initial backfill**: `pnpm backfill <subcommand>` (`scripts/backfill.mjs`). `scripts/lib/*.mjs` is a **duplicate implementation in plain JS** of the normalization/mapping/fingerprint logic in `src/lib/` (the scripts must run directly via `node scripts/backfill.mjs`, so they cannot import TS that uses the `@/` path alias) — **`src/lib/bond/fingerprint.ts` and `scripts/lib/fingerprint.mjs` must produce identical fingerprints** (if they diverge, what the backfill loaded and what cron computes differ, and every issue is misjudged as "changed"). If you change one of them, do not stop there — cross-verify with the `fingerprint-parity-check` skill.
  - For `apply --source issu|price --remote|--local [--budget 90000]`, `--remote` and `--local` do different accounting. **Only `--remote` reads and writes `.backfill/state.json`** — it tracks per-chunk `applied`/`appliedAt`/`actualRowsWritten` plus the D1 free tier daily write limit (`dailyWrites`, reset at UTC midnight) so it can skip already-applied chunks and stay within budget. `--local` ignores that ledger entirely (Miniflare SQLite has no write limit, so it re-applies all chunks in full every time). Moving to Paid made this write-budget accounting unnecessary (50 million writes/month included), but since the backfill is already complete **the code stays as-is** — it is kept so the next person reading this file does not wonder "why is there a ledger here". `pnpm backfill status` always reports against remote only.
  - To populate local development data, reuse the chunks already generated in `.backfill/sql/` (no re-collection needed): `pnpm db:reset:local && pnpm seed:local` (`package.json`) — this runs reset of `.wrangler/state/v3/{d1,r2}` → migrations → full issu/price application → `pnpm snapshot:local` in one go. `.backfill/` is git-ignored (319MB), so if it gets deleted the open API has to be scraped again.
- **Screener snapshot — base (weekly) + bond delta (every business day)**: basic info is collected every business day (see the "cron pipeline" section above), but rebuilding the base (`snapshot/bond/{basDt}.json`, ~3MB, `immutable` cache) daily would make visitors re-download the whole thing every day. So the base is fully rebuilt (compacted) only on `SNAPSHOT_REBUILD_WEEKDAY_KST` (Wednesday by default, `src/lib/sync/config.ts`), and on other weekdays a small **bond delta** containing only the issues that changed that day is uploaded (`snapshot/bond-delta/{basDt}.json`) — this extends the base+delta pattern prices already used (see the "Read layer — list" section below) along the bond axis. The branch in `src/lib/sync/plan.ts`: if `issu` is `done` for today's basDt and the base does not yet exist for that basDt (either it is a rebuild weekday or there is no base at all), it is `snapshot`; otherwise `bondDelta`. Even if a base rebuild exhausts `SNAPSHOT_MAX_ATTEMPTS` and gives up, it automatically falls back to `bondDelta` to stay current.

  **basDt identity rule (important)**: the base's R2 key, `index.json`, and `app_meta.snapshot_bas_dt` always use the "collection target basDt" (the basDt that tick's `issu` run queried) — never the maximum of `bond.last_chg_bas_dt`. `createSnapshotBuilder().finish(basDtOverride)` in `src/lib/snapshot/encode.ts` takes that override, and `buildAndPutSnapshot(env, targetBasDt)` always passes it. Violating this leads to misjudged rebuilds on every tick, or to overwriting an `immutable` cache key with different content so clients can never receive it (details in `snapshot-sync-reviewer`). `scripts/build-snapshot.mjs` (the manual fallback) has no notion of a "collection target", so it keeps the existing `MAX(last_chg_bas_dt)` behavior with no override.

  The base build reads four sources — `bond` (static fields) + `bond_state` (current values, `LEFT JOIN`) + `code_label` + the "latest" price per issue (joining `bond_price` via a `MAX(bas_dt)` subquery) — through `src/lib/d1/snapshot-repo.ts` with **keyset pagination** (ascending `isin_cd` chunks, `SNAPSHOT_CHUNK_SIZE=5000`), streaming them sequentially into `createSnapshotBuilder()` — not using a full `all()` because of the 128MB isolate memory constraint is the key design point. Page termination is decided by the number of **distinct** `isin_cd` values in the page, not by the number of rows received (`distinctIsinCds`) — because one `isin_cd` can yield two rows, KTS and 일반채권.

  The **bond delta** (`src/lib/snapshot/bond-delta.ts`, `buildAndPutBondDelta`) obtains that day's changes by re-querying D1 (`SNAPSHOT_BOND_CHANGED_SQL`: `WHERE b.last_chg_bas_dt = ?1 OR s.valid_from = ?1` — covering exactly "a change to bond static fields (including newly listed issues) OR a change to bond_state (credit rating, outstanding balance)"). Unlike a price delta row (which holds only the changed fields), one delta row holds that issue's **entire current state as of that day**, so even as multiple dates accumulate, overwriting in ascending basDt order alone leaves the latest state (`mergeBondDeltas`). `bond_isur_nm` is carried as the raw string (the delta does not know the base's `issuers` dictionary) and is interned into that dictionary at merge time. If the number of changed rows exceeds `BOND_DELTA_MAX_ROWS` (5000), it falls back to a full rebuild (`tooLarge`, `runBondDeltaAction`).

  `pnpm snapshot -- --remote|--local` (`scripts/build-snapshot.mjs`, **the target must be specified** — running it with no arguments exits(1); the local shortcut is `pnpm snapshot:local`) is now used for only two purposes: (a) seeding local dev (called internally by `pnpm seed:local`) and (b) a manual remote fallback when the cron pipeline is stuck — it queries D1 in full in one shot (no chunking) and encodes with `src/lib/snapshot/format.ts` (v2 format: column-oriented arrays, issuer dictionary, dates as epoch days) (measured rows_read: 577,729). Unlike the backfill scripts, this script does not re-implement the logic in `scripts/lib/*.mjs` — it **imports `src/lib/snapshot/format.ts`/`encode.ts`/`index-file.ts` directly by relative path**, because those three files are written without the `@/` alias so Node 24's type stripping can execute the `.ts` as-is (back in the backfill-script era we did not know this technique, so we worked around it with a duplicate plain-JS implementation). **The cron path (`build.ts`, chunked queries) and the script path (full query) use completely different D1 queries, but they share one copy of the encoder (`createSnapshotBuilder`/`encodeSnapshot`) and the index-update function (`applyBondSnapshotToIndex`)** — the two paths' outputs must not diverge byte-for-byte (the issuer dictionary indices are determined by row arrival order, and the guarantee is that both paths insert rows only in ascending `isin_cd` order), so do not break that sharing when changing snapshot-related logic — `tests/workers/snapshot-build.test.ts` regression-checks that the two paths' outputs match under `JSON.stringify`.
- **Snapshots are not compressed.** R2 stores plain JSON as-is and `/api/snapshot/[...path].ts` (`src/pages/api/snapshot/`) streams `object.body` through as a pass-through — because the Cloudflare edge automatically applies gzip/brotli to `application/json` responses based on the real client `Accept-Encoding` (a network-layer feature independent of Worker CPU; see the "edge response compression" docs). **We once stored two copies in R2 (`.json.gz`/`.json.br`) and had the Worker choose based on `Accept-Encoding`, but it did not work** — measured in local dev (the Miniflare-based Workers runtime): (1) `request.headers.get("accept-encoding")` only ever shows the value Cloudflare normalized ("br, gzip"), so there is no way to tell what the client actually sent (the real value is in `request.cf.clientAcceptEncoding`), and (2) the `Content-Encoding` header passed via `R2Object.writeHttpMetadata()` also disappeared from the final response. Verify both of these empirically before adding any new compression-related code.
- **Read (serving) layer — list**: the client fetches `/api/snapshot/index` → the base (`snapshot/bond/{basDt}.json`, immutable cache) + the bond deltas pointed to by `index.bondDeltas` (`snapshot/bond-delta/{basDt}.json`) + the price deltas pointed to by `index.priceDeltas` (`snapshot/price/{basDt}.json`) in parallel (`src/lib/snapshot/client.ts`), then merges in the order `mergeBondDeltas` → `mergePriceDeltas` (both in `src/lib/snapshot/merge.ts`, each overwriting in ascending basDt order) → `decode.ts` (conversion to `ScreenerRow[]`) — **bond must be merged first** so that an issue newly listed that day gets that same day's price delta attached. `src/hooks/useScreenerData.ts` (TanStack Query, `staleTime: Infinity`) wraps this pipeline, and `src/components/screener/BondScreener.tsx` consumes it. D1 is not involved in this path at all (list queries cause zero D1 reads). An index.json without `index.bondDeltas` (from before bond deltas were introduced) stays backward compatible because both `readIndex()` in `src/lib/r2/price-delta.ts` (server) and the `?? []` in `client.ts` (client) coerce it to an empty array.
- **Read (serving) layer — detail and time series**: the list snapshot carries only the 10 columns the screen needs, so looking at a single issue in depth queries D1 directly. `GET /api/bond/[id]` (`src/pages/api/bond/[id].ts`) returns all `bond` columns + the `bond_state` history (SCD Type 2, descending `valid_from`) + the latest `bond_price` (an array, since KTS and 일반채권 can both exist for the same `bas_dt`), and `GET /api/bond/[id]/prices` (`src/pages/api/bond/[id]/prices.ts`) returns the time series in the same column-oriented format as the snapshot, filtered by `from`/`to` (the last year by default) and `market`. `id` is either a 12-digit ISIN or a 9-digit short code (srtnCd) — the latter rides `idx_bond_srtn_cd` (partial UNIQUE, `migrations/0002_indexes.sql`). Since `bond_price`'s PK is `(isin_cd, bas_dt, mrkt_ctg)` + `WITHOUT ROWID`, time-series queries become PK range scans without any secondary index. Detail lookups keep the budget short at 3–4 D1 queries per request (`db.batch` bundles `bond`/history/latest price into a single round trip, and only the codes actually present in the response are additionally looked up in `code_label`).
  Logic lives outside the route files — split across `src/lib/d1/detail-repo.ts` (queries), `fetchBondPriceSeries` in `src/lib/d1/price-repo.ts`, `src/lib/bond/detail.ts` (snake_case rows → camelCase response conversion), and `src/lib/api/params.ts` (ISIN/srtnCd branching, date and market parameter validation, JSON response helpers). The routes (`[id].ts`/`[id]/prices.ts`) are thin shells that only compose these pieces — because the workers vitest project does not reference `main` in `wrangler.jsonc` (it cannot resolve Astro virtual modules, see the "Tests" item above), the route files themselves cannot be tested, so all testable logic was pulled out of the routes.

### MCP server

`/mcp` (`src/pages/mcp.ts`) is the MCP (Model Context Protocol) endpoint that exposes bond data to Claude (web, desktop, and mobile apps alike, as a custom connector on a claude.ai account). It is a **stateless Streamable HTTP** implementation built on `createMcpHandler` from `@modelcontextprotocol/server` (SDK v2, 2026-07-28 spec) — no Durable Object, no sessions. The factory (`createBondMcpServer`, `src/lib/mcp/server.ts`) creates a fresh `McpServer` instance per request, so no state leaks between requests.

- **Authentication is optional, and the token's role is rate-limit exemption** — not access control. The data this endpoint emits is already public via the screener UI and `/api/bond/*`, so anonymous access leaks nothing new; therefore public is the default, and only callers holding `MCP_AUTH_TOKEN` (a single shared secret, not OAuth) are released from the `BOND_API_LIMITER` limit (30 requests per minute per IP). The entire policy decision lives in `resolveMcpAccess` in `src/lib/mcp/auth.ts` (the route only calls it), and that function's comment carries the table below as the source of truth:

  | Credential | Secret configured | Result |
  | --- | --- | --- |
  | None | Irrelevant | Limit applied → proceed anonymously if it passes, 429 if exceeded |
  | Valid | Yes | Limit **exempted** → proceed authenticated |
  | Invalid | Yes | Limit consumed → 429 if exceeded, otherwise 401 |
  | Present | No | Limit consumed → 429 if exceeded, otherwise 401 |

  - **Invariant ①: every request that is not successfully authenticated consumes the limit.** A wrong token is rejected with 401 rather than downgraded to anonymous (it is better for the caller to notice immediately than for a stale token or a missed deployment to hide quietly behind "why do I keep getting 429s"), but leaving 401 outside the limit would make token brute-forcing unlimited — so the limit is consumed **before** returning 401. Do not reverse that order.
  - **Invariant ②: if there is no secret, no token can be valid.** No code path ever compares an empty-string/`undefined` secret against a presented token (preventing the accident of an empty token matching). Previously the "no secret → 503 (fail-closed)" branch also served this role, but **that branch was removed when auth became optional** (the endpoint must work publicly even without a secret), so it must now be upheld separately.
  - **The limiter is passed in as an argument rather than read directly from the binding** — there is no local Workers Rate Limiting simulator at all (see "Known Issues" above), so injecting a fake limiter is the only way to verify the 429 and exemption paths. `tests/workers/mcp-auth.test.ts` counts calls to confirm even that "when authenticated, the limiter is never called".
  - Locally, `MCP_AUTH_TOKEN="..."` in `.dev.vars`; for deployment, `wrangler secret put MCP_AUTH_TOKEN --config ./wrangler.jsonc`. **The endpoint works without it** (anonymous + limited) — with no secret, only the exemption mechanism disappears.
  - Header parsing and the 401 response are not hand-rolled; they use the SDK's `verifyBearerToken`/`bearerAuthChallengeResponse` (`requireBearerAuth` takes the whole Request, leaving no room to insert the alternate-header normalization). **Because `verifyBearerToken` unconditionally rejects a token with no `AuthInfo.expiresAt`** (SDK `dist/index.mjs`), the gate injects a synthetic expiry even though the shared secret has no expiration — do not remove it.
  - For clients that block `Authorization` as a reserved word, the alternate header `x-mcp-token` (the raw token with no prefix) is also accepted. If `Authorization` is present, the alternate header is ignored.
  - Token comparison is a constant-time XOR comparison of SHA-256 digests — workerd's `crypto.subtle.timingSafeEqual` is a Workers-only extension that this repo's type configuration does not surface on `SubtleCrypto` (it would need a cast), so only standard APIs are used.
- **The JSON Schema validator is specified explicitly.** The SDK detects the runtime and picks ajv on Node and `@cfworker/json-schema` on workerd/browsers (bundled within the package itself, so no separate install is needed), but there is no guarantee this detection resolves correctly on the real Workers runtime after Astro/Vite bundling — and ajv depends on `new Function` (an eval-family construct), which can fail on Workers. `src/lib/mcp/server.ts` forces `CfWorkerJsonSchemaValidator` from `@modelcontextprotocol/server/validators/cf-worker` via the `jsonSchemaValidator` option of the `McpServer` constructor — `tests/workers/mcp-server.test.ts` verifies this path on real workerd.
- **Three tools** (`src/lib/mcp/tools.ts`): `search_bonds` (filters by issuer / issue name / bond kind / maturity / coupon rate / KIS credit rating / outstanding balance / recently traded, plus sorting by maturity, balance, coupon rate, or volume — the only list-query path that queries D1 directly, `src/lib/d1/search-repo.ts`), `get_bond` (detail by ISIN/short code — reuses `detail-repo.ts`), and `get_bond_prices` (price time series — reuses `price-repo.ts`). `get_bond`/`get_bond_prices` add no new logic; they reuse the very query and conversion functions the `/api/bond/*` routes use. The response JSON is assembled by `src/lib/mcp/format.ts`, which does not emit the HTTP response shape as-is (the column-oriented arrays of the snapshot and time series) but flattens it into row objects so an LLM can read it easily.
- **Only `search_bonds` searches D1 directly.** Screener list queries (R2 snapshots) cause zero D1 reads, but `search_bonds` needs server-side search, so a new query was added (`buildBondSearchQuery`, `src/lib/d1/sql.ts`). The issuer/issue-name LIKE is a full scan of the `bond` table (29,079 rows as of 2026-09) — this is an intentional, tolerable trade-off given that call frequency is at human-conversation scale, and the `limit` cap (50) must not be raised.
- **Volume sorting (`sort: "volume"`) and `tradedSince` scan `bond_price` (560,634 rows) by per-issue PK seeks.** The sort target `trqu` only exists in `bond_price`, and that table has no secondary index (`0002_indexes.sql`), so a nested `MAX(bas_dt)` correlated subquery was used to read only 2–3 rows per issue (`LATEST_TRQU_SUBQUERY`, `src/lib/d1/sql.ts`). **Do not rewrite it as `(SELECT trqu ... ORDER BY bas_dt DESC, mrkt_ctg ASC LIMIT 1)`** — the result is the same, but the mixed sort directions attach `USE TEMP B-TREE FOR LAST TERM OF ORDER BY` to every issue, effectively turning it into a full scan of `bond_price` (measured via EQP). This subquery and the `tradedSince` clause go into the SQL **only when requested** — adding them unconditionally breaks the EQP regression test for the default sort path. `tests/workers/search-repo.test.ts` verifies the query plans of both paths.
- **`search_bonds`'s `kind` (bond kind) takes a Korean label, not a code.** An LLM cannot know `bond.scrs_itms_kcd` codes (1101 for 국채, etc.), and to avoid maintaining a duplicate code↔label map in the source, it is resolved via a `code_label` subquery in SQL — `BOND_KIND_LABELS` in `src/lib/bond/columns.ts` is merely a copy for exposing the zod `z.enum` choices, not the source of truth (the source of truth is D1 `code_label(domain='scrsItmsKcd')`). The credit-rating floor (`minGrade`) is expanded into an `IN (...)` list by `gradesAtOrAbove` in `src/lib/bond/grade.ts` — because string grades cannot be compared with inequality operators in SQL. That file was promoted out of `src/lib/screener/format.ts`, where `GRADE_ORDER`/`compareGrade` originally lived, in order to share them with the Worker, so `format.ts` re-exports `compareGrade` to preserve the client import path. **The mid-tier notation is `AA0`, not `AA`** (likewise `A0`/`BBB0`/`BB0`/`B0`), so dropping the suffix in `GRADE_ORDER` not only pushes the sort order back but also drops that grade entirely from `minGrade`'s `IN (...)` list — locally measured, AA0 alone accounts for 1,139 issues.
- No logic goes in the route file (`src/pages/mcp.ts`) — for the same reason as the other API routes (workers vitest cannot execute Astro route files themselves, see the "Tests" item above), it handles only routing, CORS, and calling the access-policy gate (rate limiting moved inside that gate too), while tool definitions, authentication, limit decisions, and D1 queries live in `src/lib/mcp/` and `src/lib/d1/search-repo.ts`. `tests/workers/mcp-server.test.ts` verifies this by calling `createMcpHandler(...).fetch(request)` directly, without a route — since `responseMode: "auto"` (the default) was measured to answer `tools/call` over SSE, the test helper parses both plain JSON and SSE (`data: {...}` frames).
- Local verification: after `pnpm dev`, `curl -s -X POST http://localhost:4321/mcp -H 'content-type: application/json' -H 'accept: application/json, text/event-stream' -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'` **with no auth header** must return 200 (anonymous is allowed). Check the exemption path by putting `MCP_AUTH_TOKEN` in `.dev.vars` and adding `-H "authorization: Bearer $MCP_AUTH_TOKEN"`, and check at the same time that a wrong token returns 401. You can also connect with `npx @modelcontextprotocol/inspector@latest` (headers optional). **429 cannot be verified locally** — there is no local simulator for the Rate Limiting binding (see "Known Issues" above), so unit tests cover that path instead, and the real limit is only verified after deployment.

## Open API specifications

The two Financial Services Commission bond open APIs on the Korean public data portal. **For the full field and parameter specifications see [`docs/api/README.md`](./docs/api/README.md), [`docs/api/bond-issu-info.md`](./docs/api/bond-issu-info.md), and [`docs/api/bond-price-info.md`](./docs/api/bond-price-info.md); for the corresponding types see `src/api/`.** Only a summary is covered here.

There are three sources of truth, in this priority order: ① the Swagger UI on the `openapi.do` page (the most current source of truth for response schemas and service URLs, though request parameters are empty there) → ② `GetBondIssuInfoService_V2.docx`/`GetBondSecuritiesInfoService.docx` in the repository root (the only source of truth for request parameters) → ③ the catalog `openapi.json` (`https://www.data.go.kr/catalog/15059592/openapi.json`, `.../15094784/openapi.json`) is dataset metadata only, with no parameters or schemas, so use it for reference only.

### Common conventions

- Authentication: the `serviceKey` query string (the auth key issued by the public data portal; put the Decoded value into `URLSearchParams` — beware double encoding)
- The default `resultType` is **`xml`**. To get a JSON response you must specify `resultType=json` on every request.
- **API-level errors are returned with HTTP 200.** Always check `response.header.resultCode === "00"`. **Gateway-level errors (missing/unregistered/expired `serviceKey`, etc.) are the exception: they are not HTTP 200 (401/403 etc.) and arrive in a separate envelope of the form `{"OpenAPI_ServiceResponse":{"cmmMsgHeader":{...}}}`** — undocumented in both Swagger and the docx, confirmed by real calls. The type is `OpenApiGatewayErrorResponse` in `src/api/common.ts`; for details see "공통 응답 규약" in `docs/api/README.md`.
- **The error codes were reorganized on the portal after the docx was published.** The current codes (`01/04/05/10/12/20×3/22/23/29/30/31`) differ from the docx's legacy codes (`1/10/12/20/22/30/31/32/99`), so always judge against the current table in `docs/api/README.md`. In particular, `20` is assigned to three different messages, so you cannot branch on `resultCode` alone and must look at `resultMsg` as well, and `23` (per-second call limit exceeded) is new.
- Response envelope: `response.header{resultCode,resultMsg}` + `response.body{numOfRows,pageNo,totalCount,items.item[]}`. **When a query returns 0 rows, `items` comes back as an empty string (`""`) rather than an object.**
- Paging: `pageNo`, `numOfRows`. Limits: 30 TPS, 10,000 calls/day on a development account, maximum message size 4000 bytes, average response 500ms
- Data refresh cycle: once a day, **available after 1 p.m. on business day + 1 relative to the base date** (e.g. Friday's data arrives the following Monday)
- The response fields of the bond basic info API are **all strings** (including numbers and dates). In the bond price info API, 11 price/yield/volume fields are declared as `number` in the Swagger schema for JSON, so the two APIs use different numeric conventions (see `NumericLike` in `src/api/common.ts`). Empty values arrive as `""` or the string `"NULL"`, so normalization is required in the parsing layer.

### ① Bond basic info — `GetBondIssuInfoService_V2`

- Base URL: `https://apis.data.go.kr/1160100/GetBondIssuInfoService_V2` (no `/service/` in the path)
- Operation: `getBondBasiInfo_V2`
- **Required condition**: you must pass **at least one** of `basDt` (base date) / `crno` (corporate registration number) / `isinCd` (ISIN code). Omitting all of them falls through to a query of all the latest data and times out. (The docx's request parameter table omits `isinCd`, but the detailed feature description and the portal's description both include it.)
- Optional parameters: `basDt` (YYYYMMDD), `crno` (13 digits), `isinCd` (12 digits), `bondIsurNm` (bond issuer name, max 100 characters)
- See `docs/api/bond-issu-info.md` for all 75 response fields. Key fields: `isinCd`/`isinCdNm`, `bondIsurNm` (issuer name), `bondIssuDt`/`bondExprDt` (issue date / maturity date), `bondSrfcInrt` (coupon rate), `bondIntTcd`/`bondIntTcdNm` (coupon bond vs. discount bond), `intPayCyclCtt` (interest payment cycle), `nxtmCopnDt`/`rbfCopnDt` (next / previous coupon date), `bondIssuAmt`/`bondPymtAmt`/`bondBal` (issued / paid-in / outstanding amounts), `grnDcd`/`grnDcdNm` (guarantee type), `bondRnknDcd`/`bondRnknDcdNm` (bond seniority), `txtnDcd`/`txtnDcdNm` (taxation type), `optnTcd`/`optnTcdNm` (option type), and four credit ratings (`kisScrsItmsKcdNm`/`kbpScrsItmsKcdNm`/`niceScrsItmsKcdNm`/`fnScrsItmsKcdNm`)

### ② Bond price info — `GetBondSecuritiesInfoService`

- Base URL: `https://apis.data.go.kr/1160100/service/GetBondSecuritiesInfoService` (the path **does** contain `/service/` — the most common mistake relative to ①)
- Operation: `getBondPriceInfo`
- No required parameters (every query parameter except `serviceKey` is optional)
- Filter prefix convention: `begin*` (≥), `end*` (<), `like*` (contains), no prefix (exact match). **The available prefix combinations differ per field** — do not generalize arbitrarily; use only the 20 parameters that actually exist (full list in `docs/api/bond-price-info.md`). For example, `srtnCd` only has `likeSrtnCd` (no exact match), `mrktCtg` only has exact match (no `begin`/`end`/`like`), and only `basDt` supports all four prefixes.
- `mrktCtg` (market category) values: `KTS` (국채전문유통시장, the government bond market) / `일반채권` (general bonds) / `소액채권` (small-lot bonds)
- Key response fields: `basDt`, `srtnCd` (9-digit short code), `isinCd`, `itmsNm` (issue name), `mrktCtg`, `clprPrc`/`clprVs`/`clprBnfRt` (closing price / change from previous day / yield), `mkpPrc`/`mkpBnfRt` (opening price), `hiprPrc`/`hiprBnfRt` (high), `loprPrc`/`loprBnfRt` (low), `trqu` (volume), `trPrc` (traded value)
- `xpYrCnt` (years to maturity) and `itmsCtg` (benchmark/off-the-run) are populated **only for the KTS market**.

### License (KOGL)

- **Bond basic info**: KOGL Type 2 — attribution required + **non-commercial use only**. Commercial use requires a separate data-use agreement with the Korea Securities Depository (KSD), the owner of the source data (portal@ksd.or.kr).
- **Bond price info**: no restrictions on the scope of use.
- If the service is published or monetized, check the basic-info license constraint first.
